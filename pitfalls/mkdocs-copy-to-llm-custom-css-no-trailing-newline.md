# `copy-to-llm-custom.css` shows as dirty after every `mkdocs build` / `mkdocs serve` (no trailing newline)

**Symptoms** (grep this section):
- `git status` always shows `docs/assets/copy-to-llm/copy-to-llm-custom.css` as modified after running `mkdocs build`, `mkdocs serve`, or `uv run mkdocs build --strict`
- The diff is exactly one line of "noise":
  ```diff
  -}
  +}
  \ No newline at end of file
  ```
- `git diff <file> | cat -A` confirms the only change is the trailing `\n` being stripped (no `$` after the closing brace)
- `pre-commit run end-of-file-fixer` (or the auto-fix on commit) **adds the newline back**, so the committed-into-git version always has `\n`, but the very next mkdocs run wipes it again
- This produces an infinite ping-pong: build → dirty → commit → fixer adds `\n` → build → dirty again
- Affects both `mkdocs build` and `mkdocs serve` because both go through the plugin's `on_pre_build` hook
- **No error is shown.** The plugin succeeds, build succeeds, only `git status` reveals the rewrite

**First seen**: 2026-04 on this repo, after the `c309d80 docs: bootstrap mkdocs-material site + GH Pages auto-deploy` commit landed (the `mkdocs-copy-to-llm` plugin was added then)
**Affects**: any host running `mkdocs build` / `mkdocs serve` against [`mkdocs.yml`](../mkdocs.yml) with `mkdocs-copy-to-llm v0.2.10` (and presumably earlier) when **either** `button_hover_color` **or** `toast_bg_color` is set under the `copy-to-llm` plugin block. Since this repo sets both, every machine is affected.
**Status**: worked-around by gitignoring the file (commit `24140fa`); upstream fix not yet attempted

## Symptom

After any mkdocs build cycle:

```text
$ uv run mkdocs build --strict
INFO    -  Documentation built in 1.31 seconds

$ git status
On branch main
Changes not staged for commit:
  modified:   docs/assets/copy-to-llm/copy-to-llm-custom.css

$ git diff docs/assets/copy-to-llm/copy-to-llm-custom.css | cat -A
@@ -1,3 +1,3 @@$
 :root {$
   --copy-to-llm-button-hover: var(--md-primary-fg-color); --copy-to-llm-toast-bg: var(--md-primary-fg-color);$
-}$
+}$
\ No newline at end of file$
```

The actual file content (3 lines, 119 bytes) is identical to what's in git apart from the missing final `\n`. The `\ No newline at end of file` marker is the entire diff.

## Root cause

The CSS file is **not hand-maintained** — it's auto-generated by the [`mkdocs-copy-to-llm`](https://pypi.org/project/mkdocs-copy-to-llm/) plugin (currently `v0.2.10`, in `.venv/lib/python3.13/site-packages/mkdocs_copy_to_llm/plugin.py`) on every build:

1. The plugin reads `button_hover_color` / `toast_bg_color` from the `copy-to-llm:` block in `mkdocs.yml` (lines 73-76 in this repo).
2. `_generate_custom_css()` (plugin.py:125-151) produces the contents:

   ```python
   if css_parts:
       return f":root {{\n  {' '.join(css_parts)}\n}}"
   return ""
   ```

   **Note the trailing `}}` — no `\n` after it.** This is the upstream bug.
3. `on_pre_build` (plugin.py:153 onwards) calls `_write_if_changed()` to drop the string into `docs/assets/copy-to-llm/copy-to-llm-custom.css`, overwriting whatever was on disk.

Meanwhile, [`.pre-commit-config.yaml`](../.pre-commit-config.yaml) wires up `end-of-file-fixer` from [`pre-commit-hooks`](https://github.com/pre-commit/pre-commit-hooks), which enforces a trailing `\n` on every text file. So:

```text
mkdocs build  → plugin writes "...}\n}}"            (no trailing newline)
                ↓
git status    → file dirty (1-line "diff": -} → +})
                ↓
git commit    → end-of-file-fixer rewrites to "...}\n}}\n"
                ↓
mkdocs build  → plugin overwrites again with "...}\n}}"
                ↓ (forever)
```

The plugin's `_write_if_changed()` does compare against the on-disk version before writing, but it compares its no-trailing-`\n` candidate against the with-`\n` saved version — so they're always "different" and it always writes.

## Workaround

Treat the file as a build artifact and stop tracking it. The plugin regenerates it on every `mkdocs build` (including the GitHub Actions workflow at [`.github/workflows/docs.yml`](../.github/workflows/docs.yml) that publishes the site), so committing it is redundant.

```bash
# 1. Add to .gitignore
cat >> .gitignore <<'EOF'

# Auto-generated by mkdocs-copy-to-llm plugin on every build (no trailing \n)
docs/assets/copy-to-llm/copy-to-llm-custom.css
EOF

# 2. Untrack from index, but keep the on-disk copy so local mkdocs serve
#    keeps working until the next build naturally rewrites it
git rm --cached docs/assets/copy-to-llm/copy-to-llm-custom.css

# 3. Commit
git add .gitignore
git commit -m "gitignore: untrack auto-generated copy-to-llm-custom.css"
```

That's it. `mkdocs.yml` line 80's `extra_css:` reference is fine — mkdocs reads it during `on_files` (after `on_pre_build`), so by then the plugin has already regenerated the file.

### Alternative workarounds (not chosen here)

- **Exclude from `end-of-file-fixer`** (in `.pre-commit-config.yaml`):
  ```yaml
  - id: end-of-file-fixer
    exclude: '^docs/assets/copy-to-llm/copy-to-llm-custom\.css$'
  ```
  Keeps the file in git history (good for diffing config changes over time) but creates a one-off exception to the "all files end with `\n`" lint rule. Rejected because the file isn't worth tracking.

- **Upstream PR**: fix `_generate_custom_css()` to return `f":root {{\n  ...\n}}\n"` (one `\n` added). Single-character change, zero behavioural impact. Worth doing eventually so we can drop the gitignore, but not gating this fix.

## Prevention

When adding a new mkdocs-material plugin in `pyproject.toml` / `mkdocs.yml`:

1. **Run `mkdocs build` once, then check `git status`.** If a file under `docs/assets/<plugin>/` shows as dirty with no edit on your part, suspect the same pattern: the plugin is auto-generating something whose serialisation disagrees with `end-of-file-fixer`, `prettier`, or any other formatter you have in pre-commit.
2. **Default policy: gitignore plugin-generated assets.** Hand-maintained CSS / JS / images stay tracked; anything the plugin overwrites on every build is a build artifact and belongs in `.gitignore`. Document the gitignore line with a comment explaining which plugin generates it (so the next contributor doesn't accidentally re-add it).
3. **Verify CI still works after gitignoring.** The GH Pages workflow (`.github/workflows/docs.yml`) runs `uv run mkdocs build --strict` from a clean checkout, which means the plugin must regenerate the file from scratch — confirm by reading the plugin's hooks (`on_pre_build`, `on_files`, `on_post_build`) before deleting from git.

Cross-cutting AGENTS.md rule: this is the same shape as the `modify_` / `create_` chezmoi prefix discussion ([`docs/tools/chezmoi-prefixes.md`](../docs/tools/chezmoi-prefixes.md)) — files that another tool owns should not be hand-edited or committed in their generated form. The mkdocs-plugin variant just lives outside chezmoi's source tree.
